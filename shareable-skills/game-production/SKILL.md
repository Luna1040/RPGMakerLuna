# 游戏制作工作流

把美术、运行时机制和验收证据一起交付。先识别用户当前项目、正式启动入口、已认可美术和现有生成服务。已有项目中保留其结构；这里的横版动作 RPG 是经过验证的实例，不是所有游戏必须采用的设计。

## 按任务读取

- 角色、动画、抠图、地图生成：读 [美术生产](references/art-production.md)。附带可改提示词的 H3 API 工作流、调用客户端和帧打包工具。
- 战斗、队友、任务、界面、地图：读 [Godot 制作与踩坑](references/gameplay.md)。
- 本地或团队 ComfyUI、安装与共享：读 [团队接入](references/team-api.md)。密钥不属于 skill。
- 接入、验证、导出：读 [发布门槛](references/verification.md)。

## 制作顺序

1. 确定一个可玩的短流程，记录场景、角色职责、动作与机制事件、输入和资源合同。先完成一名角色的一种动作和一个小场景，视觉通过再批量扩展。
2. 先审查精细母图，再生成协调全身动作，再处理背景和帧时序。AI 出图只是候选；必须看实际循环和游戏播放。已有用户认可素材，未要求重新设计时保持其身份和画风。
3. 保存 reference、prompt、完整 API workflow、模型文件名/版本、seed、prompt_id、history、源帧与选帧表。新的实验使用新目录。重试前查已提交任务，网络超时不代表任务未提交。
4. 游戏伤害、碰撞、状态和掉落由代码结算，图片只负责表现。动作表给出命中/释放时间，不由视频视觉猜伤害。
5. 自动检查后再人工看深浅底、循环、转向和实际战斗。交付一个明确启动入口、生成记录和尚未解决的问题。

## 必须保留的经验

- 保持角色身份不等于锁死头和躯干。动作需要髋、肩、头协调，头发披风跟随；不要把四肢摆动当完整动画。
- 全帧固定画布、脚底 pivot 和 scale。不能逐帧 bbox 居中/缩放；裁图要存统一 offset 并恢复虚拟画布。
- 母图的发丝孔洞也会把白底带入动画。要求绿幕不保证输出绿幕；本项目成功 H3 输出实际是黑底，经语义分割处理，仍需要边缘复核。
- 黑底发光特效用独立加法层；人物正常 alpha。不要整个人加法，也不要用正片叠底去黑。
- 生成的原片长度不是攻击时长。选择有效姿势、调整逐帧时长，再对齐命中事件。
- 不把排队、成功生成、人工复核、接入游戏、实机验收混为同一种“完成”。

## 随附工具

- `scripts/image_client.py`：Flux 2 Klein 9B 本机文生图/单参考图生成、断点查询和下载；默认 9315，可用 --url 覆盖。

- `scripts/comfy_client.py`：检查节点、上传母图、提交 API 工作流、续查任务和下载输出；只用 Python 标准库。
- `assets/h3-reference-api.json`：本项目验证过的 20-step H3 参数。具体节点必须由目标实例 `/object_info` 验证；模型不随包提供。
- `scripts/matte_frames.py`：给定 BiRefNet ONNX 模型，对黑底源帧生成固定画布 RGBA 和深浅底预览。结果是候选，不自动批准。
- `scripts/pack_frames.py`：按人工选帧表生成 manifest，验证 alpha、画布、透明边缘及事件时序。
- `assets/selection.example.json`：选帧数据合同示例，非已审查动作。

这是工作方法和工具包，不授予模型或素材的再分发许可。商业项目另行核查所选模型、字体和参考素材的许可证。
