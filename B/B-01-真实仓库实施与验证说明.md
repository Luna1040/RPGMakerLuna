## 已完成

### 1. 内容注册表

- 新增 `ContentRegistry` Autoload。
- 启动时加载并校验 `content/base/skills.json`。
- 所有内容使用稳定 ID；当前首个正式接入项为 `skill.knight.lightning`。
- 调用方只能取得深拷贝，不能绕过接口修改实时定义。

### 2. Agent / 工作台 Patch 边界

- 新增 `WorkbenchBridge` Autoload。
- 支持能力查询、目标读取、Patch 提交、安全点排队和撤销。
- Patch 采用乐观并发：`base_content_revision` 必须等于当前 revision。
- 相同 `patch_id` 重试为幂等，不会重复修改。
- 多操作原子提交；任一操作失败时全部拒绝。
- 战斗、跳跃、动作或存在玩家投射物时只排队，不立即改规则。
- 不接受生成的 GDScript、场景、Shader、表达式或资源路径。

当前技能白名单：

```text
/resource_cost/amount
/cooldown_seconds
/combat/base_damage
/combat/depth_radius
/combat/chain_count
/combat/chain_radius_m
```

### 3. 雷光真实数据驱动

- MP、冷却、基础伤害、纵深命中宽度、弹射目标数和弹射半径由注册表提供。
- 技能栏名称、说明、消耗和冷却同步读取注册表。
- 施法事件携带稳定 `skill_id` 和完整战斗元数据。
- 敌人投射物命中逻辑支持真实多目标弹射，并显示短暂连锁闪电线。
- `chain_count = 3` 时最多命中三个目标；不是只改 UI 或 JSON。
- 环境木箱仍保留试玩版原有命中容错，避免改变既有手感。

### 4. 存档与跨场景

- 运行时内容覆盖进入现有 `GameRuntime.snapshot()`。
- 继续由现有 `SaveStore` 负责三槽、校验和、临时文件、备份和坏档保护。
- 旧存档没有 `content` 字段时按空覆盖迁移。
- 覆盖状态绑定基础内容哈希；不允许把其它基础包的覆盖错误载入当前游戏。
- 同一会话跨场景保留撤销历史；真正从不同存档恢复时清空历史栈，但保留存档中的最终覆盖值。

## 示例：把雷光改为最多弹射 3 个目标

```json
{
  "schema_version": "runtime-patch/1",
  "patch_id": "author.lightning.chain-three",
  "base_content_revision": 0,
  "operations": [
    {
      "op": "replace",
      "target_type": "skill",
      "target_id": "skill.knight.lightning",
      "path": "/combat/chain_count",
      "value": 3
    }
  ]
}
```

工作台接入顺序：

1. 调用 `WorkbenchBridge.capabilities()` 获取 revision、目标 ID 和白名单。
2. 调用 `inspect_target("skill", "skill.knight.lightning")` 获取当前定义。
3. Main Agent 汇总子 Agent 建议并生成最终 Patch。
4. 调用 `submit_patch(patch)`；不安全时返回 `queued:true`。
5. Godot 在安全点调用 `process_pending()`，应用后返回新 revision。
6. 需要撤销时调用 `request_undo()`。

- 当前撤销栈是会话级；存档保存最终覆盖结果，不保存完整编辑历史。
- 本次没有合并 `main`，等待团队在 Draft PR 中审查。
